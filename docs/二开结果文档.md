## 1. 项目定位、范围与交付状态

Niko-Agent 是一个面向本地代码仓库的白盒编码 Agent。它以 `niko` 命令行作为统一入口，在本地工作区内协调模型、工具、权限、会话、检查点和运行证据；默认强调可审计、可恢复和敏感信息不落盘。

本次二开以 Pico 的历史设计为基础，将产品边界收敛为 Niko：包名为 `niko_agent`，发行名为 `niko-agent`，运行状态集中在 `.niko/`，项目配置使用 `.niko.toml` 和 `NIKO_*` 环境变量。兼容性策略是**不保留 Pico 的旧品牌入口**，避免一个工作区存在两套状态目录或两套安全语义。

## 2. 整体架构与关键数据流

### 2.1 模块地图

```text
niko / python -m niko_agent
        │
        ▼
cli.py ── 解析参数、加载当前工作区配置、创建或恢复会话
        │
        ▼
core/engine.py ── 单轮运行编排、模型重试、检查点、报告
 ├── config/                 配置解析与环境变量边界
 ├── providers/              Provider 抽象、客户端与错误归类
 ├── core/runtime*.py        运行时拆分的 mixin：事件、密钥、检查点、消费方
 ├── core/session*.py        session 存储、生命周期、分叉与恢复
 ├── core/permissions.py     权限 profile、审批与 worker 写入范围
 ├── core/tool_*.py          工具策略、执行、重复调用保护、工具 profile
 ├── tools/                  Pydantic schema、文件/命令/计划/提问/Agent 工具
 ├── features/               memory、skills、sandbox
 ├── tui/                    交互界面、widgets 与启动逻辑
 └── evaluation/             指标、证据、确定性评估

tests/                       单元、回归、架构边界、验收与安全测试
scripts/                     quick/full verifier、Gate8、评估入口
docs/                        用户与开发者文档
report/                      每个 Codex 会话追加式开发报告
```

核心层通过拆分职责来避免单个“万能 runtime”持续膨胀：`engine.py` 负责编排；`runtime_events.py` 管事件；`runtime_secrets.py` 管脱敏和子进程环境；`runtime_checkpoints.py` 管快照；`session_*` 管会话历史和恢复；工具权限与执行在独立模块中完成。架构边界测试同时约束模块职责和文件规模，防止后续二开把逻辑重新堆回单一文件。

### 2.2 一次 Agent 轮次的数据流

```text
用户输入 / CLI 参数
    │
    ├─► WorkspaceContext：确认项目根、配置边界与 workspace fingerprint
    ├─► SessionStore：读取或新建 .niko/sessions/<session-id>.json
    └─► Engine.run_turn
            │
            ├─► TaskState / RunStore：创建本轮 run、trace、report、artifact 目录
            ├─► Context + Memory + Skills：组装可见上下文
            ├─► Provider：请求模型，分类错误并按上限重试
            ├─► ToolExecutor：schema 校验 → 重复保护 → 权限 → 策略 → 执行
            │       │
            │       └─► 可能的文件改动：前后快照、差异与审批记录
            ├─► SessionEventBus：追加脱敏事件到 .events.jsonl
            └─► 成功结束：写入报告、更新 session、创建 checkpoint
```

重要顺序是“先校验、再执行、后持久化”。原始模型输出先用于正确解析工具调用，再经脱敏后写入 session、trace、report、memory 或事件流，避免安全处理破坏内存中的工具调用语义。

### 2.3 持久化与恢复数据流

```text
工作区可见文件（Git tracked + 非 ignored）
        │
        ▼
Checkpoint manifest（路径、哈希、大小、fingerprint）
        │
        ├─► /fork：创建子 session，父 session 只追加历史
        │
        └─► /rollback preview：生成一次性 token（10 分钟）
                  │
                  ▼
          confirm：复核 token、manifest、当前 fingerprint
                  │
                  ▼
          先备份 + journal，再按 manifest 恢复
                  │
                  ├─► 成功：生成截断历史的子 session 与恢复报告
                  └─► 失败：补偿恢复原工作区，并记录脱敏失败信息
```

快照忽略 `.git/`、`.niko/`、被 Git ignore 的内容、敏感路径与符号链接；单文件最大 16 MiB、单个快照最大 128 MiB。缺失检查点、权限状态或 workspace 一致性时采取 fail closed，而不是“尽量恢复”。

## 3. 对外接口、配置和运行产物

### 3.1 CLI 与交互命令

`niko` 是唯一面向用户的命令行入口。它支持交互式 TUI/REPL、一次性 prompt、恢复指定 session、选择模型与 Provider、审批策略、memory 与 sandbox 等运行选项；`python -m niko_agent --help` 与其共享入口语义。

| 接口 | 用途 | 主要约束 |
| --- | --- | --- |
| `niko [prompt]` | 启动交互或执行一次任务 | 从当前项目根读取配置，不向父目录继承配置 |
| `/plan`、`/plan-exit` | 进入/退出计划模式 | 计划模式只允许写当前计划 artifact |
| `/session`、`/resume`、`/history`、`/clear` | 查看、恢复、清理会话上下文 | session 事件和状态均做脱敏持久化 |
| `/fork` | 基于当前状态创建分支会话 | 子会话保持可追溯父子关系 |
| `/rollback` | 预览并确认恢复检查点 | 两阶段执行、一次性 token、10 分钟有效期 |
| `/context`、`/usage`、`/compact`、`/reset` | 上下文与用量治理 | 不把密钥或原始敏感输出写入证据 |
| memory / skills / subagent 命令 | 调用扩展能力 | 受各自 profile、写入范围和审批策略限制 |

### 3.2 配置边界

项目配置文件为 `.niko.toml`，环境变量使用 `NIKO_*` 前缀。CLI 创建 `WorkspaceContext` 时关闭父目录搜索，因此上层目录的 `.niko.toml` 或环境文件不会悄悄改变当前项目行为。`.niko.toml` 与 `.env*` 均被视为敏感路径；只有 `.env.example` 一类无凭据模板可以被正常访问。

### 3.3 `.niko/` 运行产物

| 路径 | 内容 | 安全处理 |
| --- | --- | --- |
| `.niko/sessions/` | session 元数据与追加式 `.events.jsonl` | 写入前脱敏；不应提交 |
| `.niko/runs/<run-id>/` | task state、trace、report、artifact | 原子写入 JSON，持久化前脱敏 |
| `.niko/checkpoints/` | 工作区快照 manifest 与内容 | 排除敏感、ignored、符号链接和超限文件 |
| `.niko/memory/` | working/session/daily/durable memory | 仅在允许的 memory profile 内读写 |
| `.niko/recovery/` | rollback 的备份、journal、报告 | 用于恢复补偿，不暴露密钥 |

## 4. 二开功能记录

以下每一项均按统一字段记录，方便在代码审查、面试追问或 v2 评估时回到“为什么做、改了哪里、如何证明”。涉及文件列的是主要模块，不等同于逐文件 diff 清单。

### 4.1 品牌迁移、运行目录与配置边界

**目标与背景**：将原有产品形态收敛为 Niko，消除旧品牌和旧状态目录带来的配置歧义，使用户只需要理解 `niko`、`.niko/`、`.niko.toml` 和 `NIKO_*`。

**涉及文件**：`niko_agent/__init__.py`、`niko_agent/__main__.py`、`niko_agent/cli.py`、`niko_agent/config/__init__.py`、打包元数据、`README.md`、`README.en.md`、`docs/configuration.md`、相关测试。

**设计决策**：不提供 Pico 兼容入口或状态迁移双写；使用单一品牌和单一状态根，优先降低安全和运维复杂度。配置只在当前 workspace 内解析，避免父目录配置污染子项目。

**实现流程**：CLI 解析参数后建立 `WorkspaceContext`；配置解析以当前工作区为边界，合并显式参数、`.niko.toml` 与 `NIKO_*`；随后创建 Provider、SessionStore 和 Runtime。

**接口/数据流**：`niko` / `python -m niko_agent` → `cli.py` → `WorkspaceContext` / 配置对象 → `Engine`；运行产物全部进入 `.niko/`。

**测试命令与结果**：`python -m niko_agent --help` 通过；完整离线门禁中 CLI、配置和核心运行测试通过。

**风险/限制**：不兼容旧 Pico 配置和状态目录是有意的破坏性迁移决定；用户从旧系统升级时需要自行审阅并迁移所需的非敏感配置。

**关联提交**：品牌与 v1 交付相关提交见 `53d9e33` 至 `d3a646c` 的历史；最终证据提交为 `d3a646c`。

**后续优化**：v2 如需导入旧配置，应设计显式、一次性、可预览且不读取/复制密钥的迁移命令，不应恢复运行时双兼容。

### 4.2 Runtime 编排、会话事件与运行证据

**目标与背景**：把每轮 Agent 执行变成可定位、可审计、可恢复的工作流，而非仅把模型文本输出到终端。

**涉及文件**：`niko_agent/core/engine.py`、`runtime.py`、`runtime_events.py`、`runtime_consumers.py`、`run_store.py`、`session_events.py`、`session_store.py`、`task_state.py`、`turn_history.py`、`evaluation/run_evidence.py`。

**设计决策**：运行状态按 session 与 run 两个粒度拆分；事件使用追加式 JSONL，结构化状态使用原子 JSON 写入。模型原始结果不直接落盘，先完成工具调用解析后再统一脱敏。

**实现流程**：`Engine.run_turn` 创建 TaskState/run，建立 trace；构造 prompt 和 metadata；按错误分类重试 Provider；执行工具；成功时写报告、更新 session 并创建 checkpoint。若发现 workspace identity mismatch，则不调用模型或工具而直接 fail closed。

**接口/数据流**：输入 → `Engine.run_turn` → Provider/ToolExecutor → `SessionEventBus` 与 `RunStore` → `.niko/sessions`、`.niko/runs`、报告和 artifacts。

**测试命令与结果**：完整门禁覆盖 `test_engine_acceptance.py`、`test_real_session_acceptance.py`、`test_runtime_evidence_acceptance.py`、`test_run_store.py`；Gate8 的 9 个离线真实会话场景全部通过。

**风险/限制**：运行证据只保证本地目录中的可审计性，不等同于远程不可抵赖审计；真实 Provider 调用会产生费用和数据外发风险，本次未进行。

**关联提交**：`53d9e33 feat(recovery): harden workspace recovery and secret boundaries`、`d3a646c docs: finalize Niko v1 completion evidence`。

**后续优化**：v2 可在不改变默认本地语义的前提下，增加可选的外部证据导出与签名机制。

### 4.3 工具注册、审批与最小权限

**目标与背景**：允许 Agent 操作真实代码库，同时将文件覆盖、命令执行、重复调用和越权子任务控制在明确的边界内。

**涉及文件**：`niko_agent/tools/registry.py`、`schemas.py`、`file_tools.py`、`ask_user.py`、`plan.py`、`todos.py`、`agents.py`、`niko_agent/core/tool_executor.py`、`tool_policy.py`、`tool_profiles.py`、`tool_repetition.py`、`permissions.py`。

**设计决策**：工具白名单显式注册，输入先经 Pydantic 与运行时校验；工具执行顺序固定为“校验 → 重复保护 → 权限审批 → 策略检查 → 快照 → 执行 → 差异/事件记录”。对覆盖或 patch，要求先有新鲜的 `read_file` 证据。

**实现流程**：模型只能调用已注册的 `list_files`、`read_file`、`search`、`run_shell`、`write_file`、`patch_file`、待办、计划、提问和子 Agent 工具。权限 profile 决定风险工具是否自动执行、提问或拒绝；只读/计划/worker profile 各自收缩能力。

**接口/数据流**：Provider 工具调用 → schema/runtime 校验 → `PermissionChecker` → `ToolPolicyChecker` → `ToolExecutor` → 结果、快照差异和脱敏事件。

**测试命令与结果**：`test_tool_policy_acceptance.py`、`test_tool_validation.py`、`test_permissions_acceptance.py`、`test_safety_invariants.py` 在 full gate 中通过；Gate8 覆盖计划、探索和 worker 写入范围场景。

**风险/限制**：策略控制的是 Niko 暴露的工具面，不能替代操作系统级隔离；`run_shell` 仍属于高风险能力，应由 sandbox 和审批策略共同约束。

**关联提交**：`53d9e33` 及其此前的安全恢复系列提交。

**后续优化**：可基于真实团队工作流补充更细粒度的命令 allowlist、路径 ownership 规则和审计展示，但应避免把策略写成难维护的关键字黑名单。

### 4.4 敏感路径、密钥脱敏与 fail-closed 语义

**目标与背景**：保护配置密钥、凭据与运行状态，不让模型通过文件工具、shell、事件、报告或 memory 获得或持久化敏感值。

**涉及文件**：`niko_agent/core/sensitive_paths.py`、`runtime_secrets.py`、`workspace.py`、`tool_policy.py`、`permissions.py`、`runtime_events.py`、`session_store.py`、`run_store.py`、相关安全测试。

**设计决策**：同时校验原始路径和符号链接解析后的目标路径；将 `.env*`、`.niko.toml`、`.niko/`、SSH/GPG、AWS/Azure/gcloud、Docker/Kubernetes 凭据和私钥后缀设为敏感，明确允许 `.env.example` 等无凭据模板。无法确认 checkpoint、权限或 sandbox 状态时默认拒绝。

**实现流程**：文件工具和 shell 在执行前走统一敏感路径判断；运行时从环境中识别配置密钥和秘密形态值；持久化和用户可见输出通过 redactor 处理；子进程只继承受控环境，Windows 额外保留必要的 `SystemRoot`/`ComSpec` 启动变量。

**接口/数据流**：文件/命令请求 → 原始路径检查 → resolved path 检查 → 允许或拒绝；文本输出 → secret redactor → session/trace/report/memory。

**测试命令与结果**：`test_niko_security_recovery.py`、`test_safety_invariants.py`、`test_tool_policy_acceptance.py` 和 Gate8 的 security rejection 场景均通过。

**风险/限制**：密钥模式识别和路径规则无法替代企业级 DLP；用户仍不得把真实凭据提交到仓库或粘贴进普通任务上下文。

**关联提交**：`53d9e33 feat(recovery): harden workspace recovery and secret boundaries`、`cb9e759 fix(recovery): fail closed on workspace mismatch`。

**后续优化**：新增 Provider 或凭据类型时，应同步扩展敏感路径/变量测试；可以评估 OS 凭据库集成，但必须先明确数据主权和跨平台方案。

### 4.5 Checkpoint、Fork 与 Rollback 恢复协议

**目标与背景**：让 Agent 的改动可检查、可预览、可恢复，避免误操作后只能依赖人工猜测或直接 Git reset。

**涉及文件**：`niko_agent/core/runtime_checkpoints.py`、`session_branch.py`、`session_lifecycle.py`、`workspace.py`、`artifacts.py`、`session_store.py`、`run_store.py`、恢复与安全验收测试。

**设计决策**：checkpoint 从 Git 可见文件（tracked 加 non-ignored）建立 manifest；恢复采用“两阶段确认”，先预览再凭一次性 token 确认。恢复前建立备份和 journal，失败后执行补偿恢复；父 session 只追加，恢复或 fork 产生可追溯的子 session。

**实现流程**：执行风险工具或成功轮次时按需建立检查点；`/fork` 创建关联子会话；`/rollback` 先输出 preview/token，confirm 时重新校验 token、有效期、manifest 与 workspace fingerprint，随后恢复并写 recovery report。

**接口/数据流**：工作区文件 → manifest/hash → checkpoint；`/rollback preview` → token（10 分钟）→ confirm → backup/journal → restore 或 compensation。

**测试命令与结果**：`test_niko_security_recovery.py`、`test_workspace.py`、`test_real_session_acceptance.py` 在 full gate 中通过，覆盖 token、fingerprint、恢复失败补偿和父子会话行为。

**风险/限制**：快照有 16 MiB 单文件和 128 MiB 总量限制；不覆盖 ignored、敏感或符号链接文件，因此它不是任意目录的完整备份系统。

**关联提交**：`cb9e759`、`53d9e33`、`d3a646c`。

**后续优化**：可为大文件/二进制资产提供显式的外部备份适配器；须保持 preview、容量预算和 fail-closed 恢复约束。

### 4.6 子 Agent 与受限并行工作

**目标与背景**：让主 Agent 可以把独立探索或有明确写入范围的任务委派出去，同时保持主 Agent 对计划、集成、验证和提交的唯一责任。

**涉及文件**：`niko_agent/core/worker_manager.py`、`worker_execution.py`、`worker_runtime.py`、`worker_notifications.py`、`worker_artifacts.py`、`niko_agent/tools/agents.py`、`permissions.py`。

**设计决策**：区分 `Explore` 与普通 worker。Explore 只读、审批为 never；普通 worker 只有在显式 `write_scope` 内才能写入，并且不能使用 shell。子 Agent 使用独立运行状态和模型工厂，主 Agent 汇总通知与产物。

**实现流程**：主 Agent 发起任务 → WorkerManager 建立 per-session worker 状态 → 子运行时执行受限工具 → 产物和事件进入 worker artifacts/notifications → 主 Agent drain 后决定下一步。

**接口/数据流**：`agents` 工具 → `WorkerManager` → 独立 worker runtime → 通知/工件 → 主会话。

**测试命令与结果**：`test_agent_workers_acceptance.py` 与 Gate8 的 `worker_write_scope` 场景通过。

**风险/限制**：并行不会自动解决共享文件冲突；同一文件或强耦合模块仍应由主 Agent 串行处理。真实 Provider 并发会增加费用和数据外发面。

**关联提交**：v1 完成系列中的 worker 验收与运行时提交，最终交付证据见 `d3a646c`。

**后续优化**：v2 可增加只读代码地图、任务依赖图和冲突预检，但不应放宽默认 worker 的 shell/写入边界。

### 4.7 Plan Mode 与 Todo Ledger

**目标与背景**：将“先规划、再执行”的协作方式固化为产品能力，并让长任务的状态对用户可见。

**涉及文件**：`niko_agent/core/plan_mode.py`、`todo_ledger.py`、`task_state.py`、`niko_agent/tools/plan.py`、`todos.py`、`commands/slash.py`、`tui/`。

**设计决策**：计划模式不是普通写权限的别名；它只允许写入当前计划 artifact，并要求结束前具有计划产物。待办账本与任务状态分离，避免把 UI 提示当成真实执行状态。

**实现流程**：`/plan` 进入受限 profile；模型通过计划工具形成 artifact；`/plan-exit` 回到常规模式。Todo Ledger 在每一轮中维护待办项、状态和说明，TUI/CLI 根据任务状态展示进展。

**接口/数据流**：slash command → `PlanMode` / `TodoLedger` → 工具 schema → session/run 状态与用户展示。

**测试命令与结果**：`test_todo_ledger_acceptance.py`、`test_task_state.py`、`test_context_governance_acceptance.py` 及 Gate8 的 plan/todo/explore 场景通过。

**风险/限制**：计划 artifact 仍是文本性协作物，不替代用户对跨模块、架构或安全变更的确认权。

**关联提交**：v1 功能实现提交及 `d3a646c` 交付证据。

**后续优化**：可为 v2 计划增加结构化风险、验收项和依赖字段，同时保留自然语言可读性。

### 4.8 Memory 与 Skills 扩展机制

**目标与背景**：在不把运行目录变成无边界知识库的前提下，提供可控的长期记忆和可复用技能。

**涉及文件**：`niko_agent/features/memory.py`、`skills.py`、`skills_bundled.py`、`skills_runtime.py`、`niko_agent/core/context_manager.py`、`compact.py`、相关工具、命令和测试。

**设计决策**：memory 分为 working/session、daily、durable topic 和 `MEMORY.md` 四层；技能区分内置、用户和项目来源，可内联或 fork 执行。技能运行使用临时允许工具 profile，dream profile 才能写 `.niko/memory`。

**实现流程**：上下文管理器按预算选取记忆与技能信息；`/remember` 写入指定层；`/dream` 由专用 profile 汇总/整理，并以默认 24 小时、5 session 的节奏避免高频自动写入。即使关闭 memory，freshness 的安全状态仍保持。

**接口/数据流**：用户命令/自动规则 → Memory/Skills runtime → 受限工具调用 → `.niko/memory` 与会话上下文。

**测试命令与结果**：`test_memory.py`、`test_skills_acceptance.py`、`test_context_manager.py` 在 full gate 中通过；Gate8 覆盖 inline skill 场景。

**风险/限制**：记忆会影响后续 prompt，错误或过时内容可能造成上下文偏差；因此记忆写入仍需脱敏、预算控制和可追溯来源。

**关联提交**：v1 功能实现系列与 `d3a646c`。

**后续优化**：可引入记忆过期、来源评分和显式删除/导出体验；需要先定义哪些内容属于项目资产。

### 4.9 Sandbox 与 Windows 命令执行兼容性

**目标与背景**：让 `run_shell` 在可用平台获得额外进程隔离，同时确保隔离后端缺失时不会伪装成安全执行。

**涉及文件**：`niko_agent/features/sandbox/`、`niko_agent/core/runtime_secrets.py`、`tool_executor.py`、`scripts/verify.py`、`docs/sandbox.md`、sandbox 测试。

**设计决策**：提供 `off`、`best_effort`、`required` 三种模式。Linux 采用 bubblewrap；`required` 下后端不可用即拒绝，`best_effort` 降级并写事件。Windows 使用 `cmd.exe /d /s /c` 并最小化子进程环境，减少 AutoRun、缺失 HOME 与复杂引号造成的启动异常。

**实现流程**：工具执行前根据配置选择 sandbox runner；runner 检查平台和后端可用性；构造受控环境与命令行；结果经红线规则和脱敏后返回运行时。

**接口/数据流**：`run_shell` → 权限/策略 → sandbox mode → 平台 runner → 子进程输出 → redactor/运行事件。

**测试命令与结果**：`test_sandbox_config.py`、`test_sandbox_runner.py`、`test_verify.py` 在 full gate 中通过；verifier 的各阶段具有边界超时，超时时只清理自己创建的进程树。

**风险/限制**：Windows 当前没有 Linux bubblewrap 等价后端；因此 `required` 模式应拒绝执行而不是宣称已隔离。sandbox 也不是绕开工具策略和审批的替代品。

**关联提交**：`d8718d6 fix(verify): bound offline gate process lifetime`、`53d9e33`。

**后续优化**：如要引入 Windows 专用隔离后端，需单独评估权限模型、可观察性、CI 可用性和失败时的 fail-closed 行为。

### 4.10 离线验证、Gate8 与确定性评估

**目标与背景**：避免只用“能启动”来判断 Agent 是否可交付，建立不依赖真实 Provider 的本地质量门禁。

**涉及文件**：`scripts/verify.py`、`scripts/evaluate.py`、`niko_agent/evaluation/evaluator.py`、`metrics.py`、`run_evidence.py`、`tests/test_verify.py`、`tests/test_evaluator.py`、验收测试。

**设计决策**：full verifier 顺序执行 Ruff、pytest、Gate8 与确定性评估；每一阶段有超时边界，超时仅终止 verifier 自己创建的子进程树。确定性评估必须显式带 `--deterministic`，确保不会误调用真实 Provider。

**实现流程**：`verify.py --profile full` 收集每阶段结果；Gate8 启动九类离线真实会话；`evaluate.py --deterministic` 运行 12 项脚本化任务并记录指标/证据。指标时间戳改为 timezone-aware，避免运行时弃用警告和跨时区歧义。

**接口/数据流**：源码与测试 → verifier phases → 每阶段结果/超时控制 → evaluation metrics/evidence → 总体交付结论。

**测试命令与结果**：见下一章的完整验证记录；全部离线必经阶段通过。

**风险/限制**：离线脚本覆盖的是可重复的协议与行为，不能证明所有真实模型、网络和第三方 Provider 组合均可用；真实 smoke 必须在单独授权、脱敏和费用可控的条件下进行。

**关联提交**：`d8718d6 fix(verify): bound offline gate process lifetime`、`bceee1a fix(metrics): use timezone-aware capture timestamps`、`d3a646c`。

**后续优化**：v2 可以补充基准趋势、性能阈值和平台矩阵，但不得将带真实密钥的 smoke 变成默认门禁。

## 8. 已知问题、风险与 v2 候选项

### 8.1 Windows 超长临时路径的 session event 持久化

在经典 Windows 路径限制仍生效的环境中，如果临时根目录很深，`.niko/sessions/<session-id>.events.jsonl` 的完整路径约达到 269 个字符时，事件文件创建/写入会失败。使用短临时根时 full gate 完整通过；使用深层临时根时曾引发 8 个与 session event 持久化相关的测试失败。

这不是当前常规短路径工作区下的 v1 功能失败，但属于跨环境兼容性风险。用户已明确要求本轮**不修复**，因此当前处理是：

- 在本文、`progress.txt` 和会话报告中透明记录；
- 不修改源码、不新增“假通过”分支；
- 作为 v2 规划时需要评估的候选需求，而非本轮已完成项。

可能的技术方向包括缩短 session 文件命名、将可配置/临时运行根规范化为短路径，或在创建持久化文件前给出明确诊断。选型前需验证其对恢复语义、并发 session、用户目录约定和现有测试的影响。

### 8.2 其他风险控制

| 风险 | 当前控制 | 后续条件 |
| --- | --- | --- |
| 真实模型/Provider 不确定性 | 默认离线门禁不调用真实 Provider | 单独授权、使用测试账户、限制费用并脱敏日志 |
| 远程仓库状态变化 | 本地提交已完成，未 push/PR/merge | 明确远程分支和操作授权后再执行 |
| 大文件与 ignored 文件恢复 | checkpoint 有 16 MiB/128 MiB 上限并排除不安全内容 | 需要时设计外部备份，不放宽默认安全边界 |
